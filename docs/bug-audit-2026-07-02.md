## 1. [P1] list_milestones is defined three times; the effective definition sends a POST (gh api -f without -X GET) that always fails HTTP 422

## 4. [P1] StageResult.RETRY_FREE is unhandled in the concurrent scheduler — free-retry tickets are silently dropped as FAIL

`services/sprint_manager/concurrent_scheduler.py:270` — dimension: orchestrator, verifier confidence: high

The worker's test-result dispatch handles PASS, EXHAUST, REJECT, and treats everything else as StageResult.FAIL (`else: terminal.add(t); result.dropped.append(t)`). But pipeline._tester_stage (pipeline.py:1044) returns StageResult.RETRY_FREE for a transient merge-conflict rebase race, expecting a requeue that does not burn an attempt (both _run_serial and _run_pipeline in pipeline.py handle RETRY_FREE explicitly; this scheduler does not). In concurrent mode the ticket is marked terminal and dropped: no requeue, no _finalize_skip (the stage already returned early after printing 'free retry'), no needs-rework label, no on_dropped (pipeline passes none). Merge races between sibling tickets are precisely the case concurrency makes MORE likely.

**Failure scenario:** max_coder_slots=2; tickets A and B in the same level both pass coding; A merges first; B's merge-preview hits a conflict against the moved base → _tester_stage prints 'merge conflict (likely rebase race) — free retry 1/3' and returns RETRY_FREE → scheduler's else-branch marks B terminal/dropped. B's IssueState stays 'tester_done', its GitHub labels stay SIT/in-progress, it appears in neither merged nor skipped, and the sprint finishes without ever re-dispatching it.

**Verifier:** Confirmed by direct code reading. (1) concurrent_scheduler.py has zero references to RETRY_FREE (grep across services/sprint_manager hits only pipeline.py); the worker's test-result dispatch (lines 250-274) handles PASS/EXHAUST/REJECT and its final `else:  # StageResult.FAIL` branch (line 270-274) does `terminal.add(t); result.dropped.append(t)` — so RETRY_FREE falls into the drop branch. (2) pipeline.py:1044 `_tester_stage` really does return `_StageResult.RETRY_FREE` on a changed-signature MERGE_CONFLICT within MERGE_CONFLICT_FREE_RETRIES, returning early BEFORE record_failure/_finalize_skip/_transition_safe — so no skip finalization, no label change, no needs-rework transition happens for that ticket. (3) That exact `_tester_stage` is passed as test_fn to run_concurrent_level at pipeline.py:1177 whenever state.max_coder_slots > 1; the call site passes on_merged and on_needs_rework but NOT on_dropped (pipeline.py:1181), so the drop triggers no callback — the ticket silently disappears from the sprint (in summary.processed but never in merged or skipped, IssueState left in its intermediate status). (4) No guard elsewhere: the serial path (run_level pipeline.py:183) and the two-slot _run_pipeline (pipeline.py:300) both handle RETRY_FREE explicitly by requeueing without incrementing attempt, proving the contract the concurrent scheduler violates. RETRY_FREE is reachable in concurrent mode — nothing gates the free-retry branch on serial execution, and sibling merges within a level (the trigger) are exactly what multi-slot concurrency produces. Severity P1: an autonomous sprint silently loses a ticket with no alert, no rework label, and inconsistent state.json, and the trigger probability scales with the concurrency feature itself.
